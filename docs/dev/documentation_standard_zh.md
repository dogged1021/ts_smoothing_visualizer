# 算法文档更新标准

本规范适用于以后新增或修改的方法，包括滤波、求导、频谱分析与干扰抑制。文档与代码在同一开发小步交付，不能仅在最终回复中介绍。

## 新增方法必须配套独立 Markdown

- 每个新方法在 `docs/` 创建独立 `.md`，名称应稳定、能辨认算法，例如 `butterworth.md`、`fft.md`、`notch.md`。
- 新增具有不同计算或时间语义的方法变体，也应有独立介绍页；可链接已有原理，仅补充差异，避免复制长篇内容。已有方法的普通参数调整不需要新建文件。
- 在 `docs/overview.md` 添加入口；相关旧文档、开发计划及阶段检查说明同步更新，删除已过时的“尚未实现”描述。
- 若只是提出规划，明确写“计划实现”，不能把拟调用的库或预期效果写成已经实现。
- 文档以简洁中文为主，保留必要英文算法名、公式与 API；源码相对链接和官方资料链接应可定位。

## 每页最少内容

1. **任务与直觉**：估计什么、输出什么，一句话解释核心思想。
2. **数学原理**：关键公式，解释符号、单位及输入假设；容易混淆的方法给一个短例子。
3. **参数和效果**：默认参数、调大调小的影响；区分函数默认值、页面默认值。
4. **优缺点**：适用条件和典型失败场景，不只写“平滑效果好”。
5. **变体与时间语义**：中心/单边、单向/双向、因果性、启动、未来等待、响应滞后；不适用的项目明确说明。
6. **本项目实现**：源文件/函数、库与关键调用参数、边界及初始化、有效点规则；区分库能力与页面已经开放的能力。
7. **注意事项与验证**：采样率、量纲、数值误差、异常/短数据限制，至少一个可检查的性质或例子；链接官方依据。

不要求所有算法都有中心/单边版本，不把算法家族能力等同于当前实现。正文尽量一到两屏；必要推导可以折叠或链接，不强制堆满所有章节。

## 交付检查

- 新方法文档、索引、当前实现范围一致；不遗漏新增入口。
- 公式的 Δt、Hz、方差/标准差及输出时间对齐正确。
- 示例用当前实现核验，局部链接有效；文档修改本身不要求重复跑全套数值测试。
- 实现变更仍需相应数值和页面检查；有意保留的误差与边界限制写入文档。
- 每个小步结束附英文 commit 建议，不自动提交，停下来供用户检查。
